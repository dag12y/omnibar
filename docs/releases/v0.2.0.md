# v0.2.0 — 2026-11-13

Omnibar adds application launching, unified app/window search, optional previews,
and saved window arrangements to its themed desktop panel.

- **Apps:** search installed desktop applications and launch through GIO.
- **Search:** find apps and running windows together; open it from the header
  or with Ctrl+K while the panel has focus. Switch/Launch remain explicit.
- **Preview:** request a bounded, in-memory thumbnail of one running window in
  Windows or Search. Requires `grim>=1.5.0`; there is no background capture.
- **Controls:** move an exact window to a workspace, float/tile it, or
  maximize/restore it while keeping the panel open.
- **Saved layouts:** save a named workspace arrangement and restore matching
  open windows, floating geometry, and window states. Delete saved layouts or
  save the same name to update them.

## Install or upgrade

Verify the release assets with `sha256sum --ignore-missing -c SHA256SUMS`, then
install `omnibar-0.2.0-4-x86_64.pkg.tar.zst` using `sudo pacman -U`. Restart the
backend with `systemctl --user restart omnibar.service`. Restart the UI to load
updated QML, then use `omnibar-toggle` to reopen the panel.

Existing config and user files are preserved. In your existing
`~/.config/omnibar/config.toml`, Apps requires `process.manage`; Windows controls
and layouts require `window.manage`; previews additionally need `screen.capture`.
Restart the backend after changing grants. These optional grants remain disabled
in the example. GIO (`glib2`) is now an explicit runtime dependency.

Saved layouts explicitly persist app names and window titles as private JSON in
`$XDG_DATA_HOME/omnibar/window-layouts.json` (normally
`~/.local/share/omnibar/window-layouts.json`). There is no automatic save or
startup restore. Ordinary window listing, previews, and searches stay in memory.

## Limits

Open the matching apps before restoring. Missing/ambiguous windows and changed
monitor arrangements are rejected; pinned/grouped/fullscreen windows are not
supported. Floating geometry is restored, while tiled order follows Hyprland's
current layout. Restore is a sequence of confirmed actions: a later failure can
leave partial changes and is reported. Exact background maximize/restore
requires Lua-configured Hyprland; unsafe focused-window fallback is never used.
Limits are 8 layouts, 16 windows per layout, and 64 KiB of stored data.

Verified on x86_64 Omarchy/Hyprland. aarch64 runtime testing and a physical reboot
were not performed. See the
[verification record](https://github.com/dag12y/omnibar/blob/main/docs/releases/v0.2.0-verification.md)
and [installation guide](https://github.com/dag12y/omnibar/blob/main/docs/development/packaging.md).
